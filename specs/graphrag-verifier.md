## 1. Product spec

**What it is.** A document question-answering system where retrieval is permission-aware and every answer claim is citation-verified. Documents and chunks carry sensitivity + access-control (ACL) labels. Permission filtering happens **in code, before retrieval results reach any model** — the model never sees a chunk the requester can't access. A graph layer over entities and relations answers multi-hop questions that flat similarity search misses. A verifier checks every claim in the answer against its cited chunks before the answer is shown.

**Who it's for.**
- Sensei itself: its knowledge module, so a personal agent answering from a multi-user corpus (a family's, a team's) can be trusted not to cross permission lines.
- Small teams and startups who need Glean-style enterprise search discipline without Glean's price — and who need to *prove* it doesn't leak, not just believe it.
- Reviewers (the FDE demo): anyone can log in as a low-privilege user and try to break it.

**v1 scope (Week 1, sized to two 3-hour blocks).**
- Frozen **synthetic** corpus only: a fictional company generated by a script with a fixed seed — roles/groups (Engineering, Sales, HR, Finance, Exec), sensitivity tiers, per-document ACLs, and planted canary documents with unique fake secrets per restricted group (leak detection is mechanical, no judge needed).
- Ingest → chunk (metadata rides with every chunk) → dense + BM25 indexes → ACL pre-filter → flat RAG answering with mandatory citations.
- Graph layer: entity/relation extraction, permissioned traversal, multi-hop question path.
- Verifier: deterministic citation checks first (see §2), model judge only for the residue, labelled as opinion.
- Eval harness v1 (§3) with the permission hard gate, run at k=3, first numbers published in the README.
- Minimal demo surface: a query interface with a role switcher ("ask as Sales / ask as HR") — enough for the try-to-break-it demo. No polished UI.

**Explicit non-goals for v1.**
- No real private documents, ever. Synthetic corpus only — this is also what makes the evals publishable.
- No live connectors (Drive, Notion, Slack). File-based corpus only.
- No training or fine-tuning any model.
- No hosted multi-tenant service. Local demo + public repo.
- No graph community/cluster summaries in v1 — summaries inherit the strictest member ACL or they silently leak; that design problem is named here and deferred to v2, not smuggled in.
- No model routing or second-agent machinery (that is MergeJudge / the Sensei router's territory).

## 2. Architecture sketch — Sensei patterns reused

The design deliberately reuses patterns already proven in Sensei, so the module composes with the rest of the system instead of inventing a second security philosophy:

- **PermissionGate pattern: permissions enforced in code, never by prompt.** The ACL filter is applied inside the retrieval query itself. By the time any text reaches a model, everything in it is already permitted for the requester. A prompt that says "don't reveal restricted content" is a request; a filter in code is a gate. Only the gate counts.
- **Deterministic verification first (code checks; models opine).** The verifier runs in two layers:
  1. *Deterministic checks (code, pass/fail):* every claim has a citation; every cited chunk ID exists; every cited chunk was in this request's retrieved set; every cited chunk's ACL includes the requester. Any failure = answer blocked, no model involved in the decision.
  2. *Entailment residue (model judge, labelled opinion):* for claims that pass layer 1, an NLI/judge check asks whether the cited chunk actually supports the claim. Its output is reported as a labelled opinion with a confidence, never silently merged into the pass/fail numbers.
- **Traces with redaction (Sensei observability pattern).** Every answer logs: requester + groups, chunk IDs retrieved, chunk IDs filtered out by ACL (count and IDs, never restricted chunk text), claims, citations, verifier results. The audit log is what makes the evals in §3 possible.
- **Graph layer.** Entities and relations extracted per document; every node and edge inherits the ACL of its source document. Traversal for a requester prunes nodes they can't access *during* traversal, not after — a path that passes through a restricted node does not exist for them.
- **Abstention is a first-class answer.** When permitted evidence is insufficient, the system says so. Guessing from general knowledge to fill a permission gap is scored as a failure mode (over-answering), not helpfulness.

Component flow: `corpus generator → chunker (+labels) → indexes (dense / BM25 / graph) → PermissionGate pre-filter → retriever (flat | graph | hybrid) → answer composer (citations mandatory) → verifier (deterministic, then judge residue) → answer + audit log`.

## 3. Eval design — SenseiBench style

- **Frozen corpus, versioned evals.** Corpus v1 is generated once from a fixed seed and frozen; its version is recorded with every result. Changing the corpus creates a new eval version — numbers from different versions are never mixed (SenseiBench frozen-version rule).
- **Synthetic only.** No real documents in any suite, so the full eval — corpus, labels, attacks — can be public in the repo.
- **Ground truth isolated from the agent under test.** Expected answers, the canary list, and query labels live with the eval harness, in storage the answering process cannot read. The system under test receives only the corpus and the query. Grading material is physically unreachable, so a high score can never be the agent reading the answer key.
- **Probes are non-vacuous.** The permission suite includes positive controls: queries the requester *is* entitled to answer, which must succeed. A system that retrieves nothing and abstains on everything scores zero on the controls and cannot "pass" the leak gate by being useless.
- **Suites:**
  1. *Correctness* — labeled queries per role; expected answer facts; scored on fact match (deterministic where the fact is a string/number; judge residue labelled).
  2. *Permission (red-team)* — adversarial queries across these attack classes: direct ask, paraphrase, role-play, multi-hop chaining, graph-traversal probing, aggregation/inference, canary extraction, prompt injection planted in a permitted document, citation-forgery pressure.
  3. *Citation* — every answer scored for citation precision (cited chunks that support a claim ÷ all citations) and citation recall (claims with a supporting citation ÷ all claims).
  4. *Multi-hop* — questions needing 2+ documents, run flat vs graph.
- **Hard gate:** any permission leak — a chunk outside the requester's access surfacing in the retrieved context, a citation, or the answer text (a canary string appearing is the unambiguous case) — **fails the entire run**, regardless of other scores. Leak-free must hold in *every* trial (pass^k on the permission suite), not on average.
- **Named ablation (Week 1): multi-hop vs flat RAG** — same corpus, same queries, same budget; graph path vs flat path on the multi-hop suite, reporting correctness and cost/latency for both. The deeper ACL-placement ablation — pre-filter vs post-filter vs prompt-only — is the research layer after Week 1.
- **Trials:** k=3 for development numbers (what Week 1 publishes, labelled as dev numbers); k≥5 required before any claim is stated as a result in a post or README headline.
- **Failure taxonomy** (every failure gets one label, published with the numbers): leak / unsupported claim / wrong citation / missed retrieval / over-abstention / under-abstention (answered when it should have refused is scored under leak or unsupported claim, by cause).

## 5. Learning checklist — explain each in your own words before the build counts as learned

- **Chunking:** what a chunk is, why chunk size and overlap change what retrieval can find, and why the ACL/sensitivity labels must be attached to the chunk, not just the document.
- **Embeddings:** a vector as a meaning-coordinate; why cosine similarity finds paraphrases but misses exact names and codes that BM25 catches (and vice versa).
- **Graph extraction:** how entities and relations are pulled from text into nodes/edges, and why a question like "who manages the team that owns the project X budget?" needs traversal that flat similarity cannot do.
- **ACL-filtered retrieval:** pre-filter vs post-filter vs prompt instruction — and what each one actually guarantees.
- **Citation verification:** why a citation's *presence* proves nothing, what deterministic checks can and cannot establish, and why entailment (does this chunk support this claim?) is the real test.
- **Why permission filtering must be code, not prompt:** a prompt is a request to a model, and injected text in a document can argue with it; code is a gate that runs the same way regardless of what any document or user says. The model cannot talk its way past a filter whose output it never sees. (This is the sentence this flagship exists to prove with numbers.)
- **Eval hygiene:** frozen versions, ground truth the system under test cannot reach, non-vacuous probes with positive controls, and why pass^k — not a single lucky run — is the unit of a publishable claim.
